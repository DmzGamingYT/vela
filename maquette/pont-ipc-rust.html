Maquette · à valider avant tout code

Un seul contrat entre l’interface et le cœur.

Aujourd’hui, 123 handlers se partagent le pont sans schéma commun : chacun caste sa charge en unknown et devine la forme attendue. Ce lot ne change rien à l’écran — il rend le pont typé, validé et déplaçable, pour qu’une coque Rust puisse un jour le remplacer sans réécrire 190 échanges à la main.

Aucune modification de l’interface

02 · Avant

Un handler sur cinq domaines différents, trois grammaires.

src/main/ipc/tabs.ts

processus principalcast
// un des 123 handlers
handle('tab:navigate', (payload) => {
  const input = (payload ?? {}) as {
    id?: unknown; input?: unknown
  }
  host.tabs.navigate(
    asId(input.id),
    asId(input.input)
  )
})

Le commentaire de asId garantit que l’identifiant est une chaîne — pas qu’il désigne un onglet existant.

src/preload/index.ts

preloadrecopie
// la même forme, écrite une 2ᵉ fois
navigate: (id: string, input: string) =>
  ipcRenderer.invoke('tab:navigate', {
    id, input
  }),

string côté renderer, unknown côté main : deux descriptions du même échange, tenues à la main.

  • Trois écritures par canal : le type dans shared/api.ts, le wrapper du preload, le cast du handler.
  • Rien ne vérifie à l’exécution : un renderer compromis peut envoyer n’importe quelle forme, seule la garde du handler l’arrête — quand elle existe.
  • Une coque Rust devrait réécrire 123 contrats qui ne sont écrits nulle part.

03 · Après

Un registre, une seule description par canal.

Le registre reprend la politique d’émetteur qui existe déjà (ipcPolicy.ts : coque, page, inconnu) et y ajoute la forme des données. Le reste est généré.

src/main/contract/tabs.ts — écrit à la main

contratsource
define('tab:navigate', {
  from: 'shell',
  input: { id: Id('onglet'), input: Url },
  output: Bool
}, ({ id, input }) =>
  tabs.navigate(id, input))

Le handler ne caste plus : il reçoit déjà la forme validée.

src/renderer/src/api.d.ts — généré

client typégénéré
// jamais écrit à la main
interface VelaApi {
  tabs: {
    navigate(
      id: TabId, input: string
    ): Promise<boolean>
  }
}

04 · Les lots

Trois lots, chacun vérifiable seul.

Registre + validation

Un fichier de contrat par domaine (tabs, notes, tunnel…), branché sur la politique d’émetteur existante. Les handlers perdent leurs casts, un canal non déclaré est refusé.

typecheck : zéro as … unknown dans ipc/
un test de refus par émetteur (coque, page, inconnu)

Client généré

Le preload cesse de recopier les signatures : il boucle sur le registre, et window.vela est typé depuis la même source.

diff : le preload perd ~200 lignes
les 45 fichiers du renderer compilent sans retouche

Transport remplaçable

Un seul module transporte les appels. Electron aujourd’hui ; un tuyau, un socket JSON ou un pont CEF demain, sans toucher aux contrats ni au renderer.

un test transporte le registre entier hors Electron

05 · Ce que l’utilisateur voit

Rien. Volontairement.

Vela — 0.3.37
mêmes onglets, mêmes gestes, mêmes réglages

Aucun écran, aucun raccourci, aucun libellé ne bouge. Le lot se mesure en revue de code et en tests, pas en captures avant/après.

  • Même contrat public : window.vela garde ses noms et ses arguments.
  • Même comportement : un canal refusé l’est déjà aujourd’hui par la politique d’émetteur ; la validation devient seulement explicite.
  • Risque borné : un lot = un domaine migré, testé, commité. Retour arrière possible domaine par domaine.
Ce que ça coûte : trois lots de refonte sans gain visible immédiat. C’est le prix d’une coque Rust qui ne réécrive pas 123 contrats implicites.

06 · Ce que ça débloque

Le même registre devient des structures Rust.

sans registre123 contrats implicites

Chaque canal est une frontière de sérialisation à réécrire à la main dans la coque. Le portage coûte des mois avant la première page affichée.

avec registreun fichier de contrat par domaine

Les entrées et sorties deviennent des structures sérialisables, générées depuis la même source. La coque Rust remplace le transport, pas les contrats.
